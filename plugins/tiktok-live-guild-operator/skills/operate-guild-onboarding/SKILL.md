# Operate Guild Onboarding

One Lead Agent coordinates two TikTok LIVE Backstage identities: the guild owner who invites, and the broker who accepts. Bind each action to the identity shown on the live page. Browser tabs in one profile share cookies; use isolated profiles when available, or switch accounts sequentially and recheck the active identity. Never put passwords, session cookies, or one-time codes in this skill or project files.

## Owner: send one invitation

1. Call `guild_workspace {}` and verify the guild name, region, and owner role. Read `guild_governance.list_organization` to check whether the target email is already a member. Check pending operation records before retrying an invitation.
2. Obtain the exact target email and destination group from the user. In LIVE Backstage **组织管理 → 组 → chosen group → 邀请成员 → 公会外部**, enter the email and confirm that it appears once in the selected list. The page says the recipient becomes a group member **after accepting**.
3. Submit once through the agent operation policy, directly in LIVE Backstage when a verified write tool is unavailable. Read **组织管理 → 操作记录** and match the email, role, group, request `加入公会`, and status. `待处理` proves an invitation is pending; it does not prove membership or delivery to the mailbox. A timeout or ambiguous result requires readback before any retry.

If `guild_onboarding.prepare_access_workflow` and `assign_staff` are exposed, execute them after exact identity and target binding. Inspect the provider response. The current `assign_staff` adapter may expect a new invitee in the member table immediately; use the operation-record pending state as the correct acceptance boundary.

For an already listed broker, use `guild_onboarding.grant_messaging_permission` with the exact AgentID and email. The adapter opens **招募主播 → 即时消息权限**, submits the platform permission change once, and requires the authorized row plus provider response before reporting success. A row that is already authorized is returned as an idempotent verified read-back.

## Broker: verify and accept

1. Open official LIVE Backstage and log in as the invited broker, checking the account identity. A second tab in the same browser profile does not isolate owner and broker sessions.
2. If the broker is already registered and logged in, do not send them to Outlook or request a verification code. Handle 验证码 only when the actual Backstage login page requires one. In that case, first check `mcp__codex_apps__microsoft_outlook_email_get_profile`. Search the newest relevant TikTok message with `mcp__codex_apps__microsoft_outlook_email_search_messages` only when the connector is authorized for the **broker's** mailbox. The owner's mailbox cannot supply the broker's code. If broker mailbox access is absent, ask the user to connect that mailbox; do not try the Backstage password at Outlook unless the user explicitly says it is also the mailbox password. Do not echo or persist a code. The current connector-to-browser path can expose a code in model-visible tool data; do not describe it as a secret-safe handoff.
3. Find the pending invitation in the broker Backstage account or its invitation email. In the observed flow, the broker chose **经纪人 → 加入公会** and saw an **邀请方** dialog naming the guild with **拒绝 / 接受** buttons. Confirm the guild is the intended one and note any account consequence shown there. Submit acceptance once and capture the broker-side result. If the page presents legal terms, preserve the exact terms and provider result in the operation record.
4. Recheck that the broker can enter the assigned Backstage area. Under the owner identity, read operation records for `已接受`, check the broker in the correct group, and inspect `guild_governance.list_permissions` for granted scope. Report acceptance only when these observations agree.

## After acceptance

The **Official account** can represent the organization. An **Affiliate Account** is the public-facing digital broker who will speak to creators. Build one identity packet before creation: a person-like display name, TikTok username, one approved base expression asset, broker-profile name, and a compatible future profile/content direction. The affiliate nickname and broker-profile name refer to the same character; a guild-brand nickname paired with a different personal broker name fails this check. Do not invent a real biography or imply a real human is typing. The six expression assets are ways the same identity can adjust to a creator, not six names or six contradictory life stories. TikTok videos, bio, avatar, and sent messages remain unverified until separately created and read back.

Bind that packet to the guild's verified business region and account country. For Atlantis, the approved provisional identity is `Mira / mira.creator_01`, the business region is MENA, and the registered country is AE. Regional adaptation changes the public language/content direction, not an already chosen name or username: plan Arabic and English versions with honest Atlantis affiliation and AI assistance. Choose each creator's conversation language from their own sourced profile or messages; ask if unclear. MENA alone is not evidence of an individual's language, nationality, religion, or gender, and must not trigger a persona switch or a fabricated local biography.

Under the owner identity, read **Creators → Scout creators → Account → Affiliate Accounts** and check for a duplicate username and existing manager before creating. The creation form takes username, nickname, and country/region. Its final **Create** also agrees to TikTok terms and acknowledges an organization account: show the exact identity and terms consequence to the human for action-time confirmation. Submit once; use the provider response and account-list readback to bind the new TikTok account ID to the approved identity. Existing accounts assigned to other brokers are not substitutes: changing manager revokes the former manager's access.

Assign only that verified account ID to the exact accepted broker. Inspect the **Change manager** dialog, choose the broker's email, submit once, and read back the manager on that same account. On the broker side, fill the broker-profile name and TikTok homepage from the verified affiliate identity. The profile contact email may be the guild owner's email, but it is distinct from the broker's Backstage registration/login email; short-lived affiliate-app login information is sent to the latter. Leave the phone to the user as agreed. Do not claim the account's videos or TikTok-app login are ready from Backstage assignment alone.

Allocate invitation cards only after the broker is accepted and the user has specified card counts. Use the guarded `guild_onboarding.allocate_invitation_cards` path when available, then compare the provider result with the live allocation table. Check broker-side conversation visibility under the broker identity; do not claim messaging works from an owner-side read. Sending a creator message requires the exact recipient and content to be authorized, followed by a provider receipt and readback.

Report staff acceptance, affiliate creation, affiliate assignment, broker profile, content, quota, and messaging as separate stages. State which identity, page, time, and provider status support each stage. Ordinary onboarding plans are `write_verified` and execute through the agent operation policy; they are reported complete only after the provider response and read-back. Broker invitation acceptance is not currently exposed as a verified `guild_onboarding` write child. Creator removal remains the only explicit approval-gated backstage action. Use the official UI and never present a plan or a filled field as a completed action.
