# TKDesk Agent

Optional creator research uses `creator_research_status` and `research_candidate` for an existing candidate's public profile and latest 10 posts. Default lookups are cache-only; enabled and explicitly authorized paid lookups use at most two fixed requests, a durable daily call budget, 24-hour default cache, no automatic retry, and source/time attribution. Missing credentials or disabling TikHub leaves native discovery, official qualification and downstream communication usable. Current deployment disables paid TikHub ranking collection. Public text supports language/content assessment; profile geography does not prove language and post engagement does not prove LIVE income. See [public research](skills/tkdesk-agent/references/tikhub-public-research.md).

TKDesk owns TikTok LIVE candidate discovery, source observations and official collection-backstage qualification. Agents select high-level country/run options through MCP and skills; ordinary Chrome remains the login and manual-verification surface. It does not send invitations or creator messages.

Direct original ranking can use either user-owned mobile authorization or an explicitly opted-in original published encrypted configuration. The latter reproduces the inspected 9.9 DownloadCoreDLL/mobileHeader request path and reports `user_authorized_original_bundle` provenance. Current MENA/SA Top/Hot/Record lists returned 99 rows each in the 2026-09-27 native-transport check, merged into 233 candidates. This source remains dependent on the publisher's current configuration; other regions and the complete qualification/enrichment/recursive chain are not established by that check. TikHub is a separate optional source and was not called in this verification.

See [the operating skill](skills/tkdesk-agent/SKILL.md), [original published configuration](skills/tkdesk-agent/references/original-published-core.md) and [parity acceptance](skills/tkdesk-agent/references/original-parity-acceptance.md). Encrypted provider files are private under the TKDesk data directory, separate from browser profiles and the user-owned Keychain Core. Use `node scripts/refresh_original_core.mjs` for an explicitly requested configuration refresh, then restart the idle daemon; normal jobs/status do not implicitly download it.

Verification: `node --test` (Node.js 22.13+). Production MCP launches through `scripts/launch_mcp` and reuses the shared daemon and SQLite store.

For an explicitly bounded sample, each country lane honors `maxFeedRounds` across pause/restart. A completed Mobile bundle is not fetched again on resume. The candidate limit stops admission independently; finite PC rounds still finish. A separate execution after completion starts fresh counters.

2026-09-27 three-round trial: SA/QA/EG each made three PC Feed attempts; original fixed Mobile bundles completed in all three lanes. Three official qualification requests checked 90 distinct creators (30 each): available 7, ineligible 83, unresolved 0. Later Feed responses were non-JSON and CurrentScore remained unknown, so this proves the observed candidate/qualification path rather than complete original parity. The bounded run is paused with its data preserved.

Source scheduling now applies the local threshold 35 to each source family separately, alternates PC/Mobile Data claims, and rotates country lanes. Fresh identity-matched Country evidence may skip a repeated foreign-country check for at most 300 seconds within one execution; the matching-country lane still performs full enrichment. Official qualification codes 11–14 have explicit labels, including `12: live_data_not_meet_requirement`. Feed and Data failures expose bounded HTTP measurements without raw responses or credentials. These changes do not establish complete league coverage or a target runtime.

Native eligible league seeds are now ready on their first scan. Inspection of 9.9 `LiveProcessor.processAnchorList` shows `SetNX Ranking:%s` with countdown/default180 as cache TTL; `RankingProcessor.process` scans `Ranking:*`, reads TTL and requests gap0/-1 immediately. Countdown is no longer a first-expansion delay. The local600second duplicate minimum remains and extends to a longer countdown. Eligible reobservation corrects old pending delays while preserving active claims and paused jobs.

Automatic ranking sweeps now distinguish an unfinished partial run from a finished bounded collection. A durable `original_collectors.executionFinished` checkpoint or a completed candidate selection prevents startup/timer replay while preserving pending seeds for explicit review. A pause received during asynchronous preflight is rechecked before resume; historical paused runs stay paused.

`status.collectionReadiness`, routed `session_status.collectionReadiness`, and `collection_route_status.readiness` expose blocking reasons for missing/unverified routes, unavailable authenticated request sessions, unchecked/incompatible collection adapters, quota, and collector ownership. Adapter readiness uses a recent observation from this daemon process, the same browser page, and the same route; historical audit evidence cannot certify a restarted session. Status reads perform no qualification request, and execution still performs its own fresh preflight. Existing stranded `reserved` qualification batches become terminal `ambiguous` outcomes on startup, retain their original quota allowance, and require explicit recheck. `commit_handoff` remains an approved local file/outbox handoff; pending outbox rows do not prove delivery or a missing platform send.

Request authorization health is separate from configuration readability. `core_configuration_status.state=ready` means the local configuration can be read; Mobile status adds `configurationState`, `onlineAuthorization`, and `onlineVerified`. An accepted fixed endpoint's explicit business success gives at most five minutes of authorization evidence, not proof of complete ranking/collection. No observation (including every new daemon process) is `unknown`; configuration may admit its first fixed request, while `productionReady` requires recent online evidence. HTTP 401/403, explicit business 20003, or the ranking transport's existing authorization-required classification fences that host's subsequent leases and queued requests for this process. Rejection is not persisted across restart, and automatic upstream renewal is not implemented. Network/429/5xx failures do not label credentials expired.

PC/Data HTTP 401/403 or explicit HTTP 2xx business 20003 (integer 20003 or canonical string "20003") immediately withdraws discovery request readiness and invalidates the current run's cookie jars and queued requests. Native `check_login` must verify the current session again, and a new run must initialize fresh jars; successful rechecking cannot reuse the old run's jars. Old responses and old login checks cannot invalidate or certify a replacement session. Safe rejection reason/time is visible without tokens, headers or response bodies. Web business 10011 remains a parameter/business rejection; it is not treated as cookie expiry. Mobile ranking retains its existing 10011 authorization-required classification without asserting that a web cookie expired.
