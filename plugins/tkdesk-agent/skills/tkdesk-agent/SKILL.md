# TKDesk Agent

Use the `tkdesk` MCP as the execution layer. The automation program owns source polling, queues, enrichment, qualification and ranking. The Agent only selects settings, performs the two startup initializations on existing official controls, starts/stops a durable task and reads its status/results; never drive the collection loop with repeated model tool calls. TKDesk has no custom desktop control panel: the only windows the user should see are isolated official-site Chrome sessions for manual login or security verification. Its durable local daemon is the collection sub-backend for jobs, candidates, deduplication, checkpoints, audit, and handoff.

This skill owns only the first stage of the workflow:

```text
TKDesk 主播名单发现 → 数字员工沟通跟进 → 营销系统运营官方账号
```

It may prepare a candidate batch, but it never sends messages, invitations, or content.

## Choose the source

In this deployment TikHub ranking collection is disabled by operator policy; normal rankings remain native. Optional public research is separate: use `creator_research_status`, then `research_candidate` for an existing candidate. Default `allowPaid:false` reads cache only. Explicit user-authorized paid research requires `allowPaid:true` and a stable unique `requestId`; profile and optional latest 10 posts require at most two calls, with durable daily budget, 24-hour default cache and no automatic paid retry. Missing/disabled provider or an error does not block discovery, official qualification, handoff or messaging. Preserve source and observed time; use bio/caption text as language/content evidence, never country as language or public engagement as LIVE income. Read [references/tikhub-public-research.md](references/tikhub-public-research.md).

- Use `source: tiktok_live`, `filters.discoveryMethod: tikhub_rankings` when the user chooses their own TikHub account for leaderboard discovery. Read [references/tikhub-ranking-adapter.md](references/tikhub-ranking-adapter.md) first. The daemon owns a finite, checkpointed snapshot plan, local deduplication and optional official qualification. `status.capabilities.discovery.tikhubRankings.state: configured` proves local configuration only. Original Mobile authorization and `modes.full_auto` parity flags do not gate this separate source. Select `tikHubRankingKind: daily|league`, `tikHubRankingPeriod: current|previous|both`, one to three existing country context seeds and a local `maxCandidates` cap. The backend selects/fixes the seed identities; the Agent supplies no IDs, URLs, cookies or keys. A context country's board can include other countries. Preserve unknown creator country and score units. A possibly charged failed/interrupted snapshot is never replayed by resume; a new paid run requires fresh explicit authorization.

- Use `collection_backstage` for the dedicated TikTok creator-collection sub-backend. It is a separate login/profile from the guild-wide operations backend and is restricted to `/portal/anchor/relation` plus the versioned read-only collection adapter. Never invoke the guild-operator skill from this workflow.
- Use `svip_legacy` when the user wants to import or filter creator rows already stored in the authorized TKsoft/svip account. This is a compatibility source, not independent discovery. The current svip page uses a username/password form; the user enters credentials in Chrome personally.
- Use `tiktok_live` when the user wants an independent discovery run from TikTok LIVE; normal regional operation is continuous and explicit bounds are optional. `regional_gift_ranking` is the target full-auto chain: country-matched PC-Web LIVE feed plus the selected display variants' fixed MobileProcessor Top/History/Hot/Record lists -> DisplayID-keyed merge -> local deduplication/DataProcessor enrichment (vendor HMD is not reproduced) -> collection-sub-backend qualification -> fixed gift-ranking expansion -> WorkID-4 enrichment and recursive qualification. This implemented shape is still not proof of a successful real live run. Before describing parity or starting a catch-up task, read [references/original-parity-acceptance.md](references/original-parity-acceptance.md) and distinguish implementation status from its separate real-E2E status. When the user explicitly asks for a candidate list without mobile ranking, choose `discoveryMethod: public_live_cards`, `mode: full_auto`: bounded public LIVE-card discovery followed by the same official collection-backstage qualification, without ranking expansion. It is a separate source, never a silent fallback or substitute for regional parity. The user completes TikTok login or QR login in its own Chrome profile.
- Use `full_auto` for authorized regional collection when `discovery.regionalGiftRanking.pcAutomationAvailable` is true and the required official sessions/preflight are ready. `modes.full_auto` / `operationalReady` still describe the stricter complete-chain evidence, so false does not globally block the available PC pipeline. Missing Mobile authorization is a named branch gap; it neither becomes an empty ranking nor proves full parity. Explicit `public_live_cards` remains a separately chosen source without regional ranking parity. Original `semi_auto` runs discovery/enrichment/filtering only: no automatic qualification or ranking, and the existing manual-import flow remains available.

## Workflow

1. Read the relevant rows in [references/original-parity-acceptance.md](references/original-parity-acceptance.md), then call `status`. Reuse the shared daemon, existing durable runs, and browser profiles. Read `core_configuration_status` and `mobile_authorization_status` before a normal regional-ranking run. `liveSampleValidated` proves only the specific route-bound sample recorded by that status; `authorizationReady` independently proves that configured mobile ranking access covers the selected country scope; read its provenance to distinguish user-owned authorization from explicitly opted-in original published configuration. Neither proves untested countries, nor that the compiled score/queue stages have passed real E2E for a country. The user-owned Core master key is generated locally by macOS Keychain. The separate optional original published source uses the original encrypted format and must be reported as `user_authorized_original_bundle`; see [references/original-published-core.md](references/original-published-core.md). The Agent may inspect or explicitly clear mobile-access metadata, but it never receives, installs, rotates, displays, or logs its value; the normal workflow must never ask the user for a supplier key or supplier credential.
2. Before opening either TikTok session, call `collection_route_status`. If no verified route exists, call `configure_collection_route` with the explicit market region, its user-confirmed member-country list, the fixed US TikTok-discovery proxy, and `collectionLanes` containing one to three atomic `{countryCode, proxyServer}` items. Array order assigns WorkID 1–3; each country appears once and each proxy must be a distinct unauthenticated loopback endpoint whose observed exit matches that item's country. Then call `verify_collection_route`, which validates the independent US discovery exit plus every configured country lane. SA, QA, and EG therefore use four endpoints total: one US discovery endpoint and one endpoint for each of the three countries. Never guess market membership, accept proxy credentials, or continue when an observed exit differs from its lane declaration. This matches the recovered original lane semantics: its three rows could select different member countries and corresponding country nodes, while `StartButtonHandler` required every selected country's `CountryData.Code` broad-region value to match (for example, all MENA rather than all the same ISO country).
3. Call `session_status` for the required session. This is a passive check and must never open, navigate, attach to, or close a browser. If it is stopped or unauthenticated, call `start_login` for `collection_backstage`, `svip_legacy`, or `tiktok_discovery` as appropriate. On macOS this opens ordinary Google Chrome with an isolated profile; tell the user to finish login there and keep that dedicated Chrome window open. `tiktok_discovery` uses the independent US route. `collection_backstage` uses `collectionLanes[0]`, the same country-matched endpoint as WorkID 1; WorkID 2 and 3 do not change that persistent browser. Changing only later collection lanes therefore does not restart either login window, while changing lane 1 requires the collection-backstage route to be rebound safely. Never ask for or handle credentials, QR contents, cookies, or tokens.
4. Call `check_login` only after the user says login is complete. It connects in place to the exact still-running dedicated Chrome over a loopback-only endpoint; it must not restart the profile. `manual_login_owner_unverified` means ownership cannot be proven and the Agent must remain fail-closed. If it reports `manual_verification` or `authentication_required`, the Agent disconnects and leaves ordinary Chrome running so the user can complete the step; never solve or bypass a challenge.
   If `collection_backstage` returns `blocked_navigation` because its existing ordinary Chrome is stranded off the official page, do not relax the allowlist or use `reset_session`. After explicit user approval, call `reopen_login` for that target and the verified route. It attaches only to the exactly verified dedicated Chrome, opens a new fixed official recovery tab, and leaves the process, persistent profile, and human tabs intact; ownership or route mismatch must fail closed. If a check reveals login or security verification is needed, leave the recovery tab for the user to complete it; never bypass a challenge. Call `check_login` only after the user has said this account is logged in or has finished a new challenge.
   Before starting TikTok discovery or making an actual automatic qualification query (not a local `manual_import`), follow both [initialize-collection-backstage](../initialize-collection-backstage/SKILL.md) and [prepare-discovery-live](../prepare-discovery-live/SKILL.md). Call the fixed `initialize_collection_backstage` and `prepare_discovery_live` tools and require both `ready: true`; inspection alone is insufficient. The generated test lookup consumes the shared query budget, never creates a candidate or invitation, and must not be replayed after a challenge. After the user confirms a challenge is solved, complete the pending initialization with `userConfirmedVerification: true`, then repeat the zero-query preflight. Confirm all discovery-profile public task pages are paused and their media time stays stable across the 3-second recheck. Missing tools or failed initialization are explicit blockers; never substitute arbitrary UI/script operations or proceed under time pressure.
5. A request to “检查、检测、看看是否正常、做健康检查或预检” is passive: do not call `create_discovery_run`, `start_run`, or `resume_run`. Use `status`, `session_status`, `collection_route_status`, and `collection_backstage_preflight`; the latter is zero-query. `calibrationProbe` still performs real platform requests and is allowed only when the user explicitly asks for a bounded live probe.
6. Create the authorized job with `countryCodes` containing one to three verified lane countries and `marketRegion` from `original_country_catalog`. Preserve all 36 original display configurations, 27 groups and 146 distinct countries/territories; the three rows limit simultaneous lanes, not catalog coverage. For a specific original display variant, pass `countryDisplayNames: [{countryCode, displayName}]` using exactly that catalog's name and permitted country. Never supply URLs, headers, tokens or arbitrary ranking selectors.
   Normal regional collection omits `maxCandidates` and `maxFeedRounds` and continues until paused/cancelled or a real session/route/qualification boundary. For an explicitly bounded sample, set either or both; finite PC round counts survive pause/restart, completed Mobile bundles are not refetched on resume, and the candidate cap stops admission independently while the requested finite PC rounds finish; `calibrationProbe: true` remains an optional diagnostic restricted to at most 30 candidates and ten Feed rounds by default. Missing Mobile authorization records that processor as `dependency_missing`, while available PC/Data/qualification continues. Read the separate real-E2E rows before describing parity: offline catalog coverage proves request/configuration support only. Each PC lane retains response cookies for the execution, waits three seconds after success or sixty seconds after ordinary error, and feeds four Data workers; full-auto qualifies thirty unattempted candidates while discovery continues. A deliberate diagnostic boundary can query a smaller tail, but pause/cancel never flushes it.
   Set `filters.highQualityMode: true` only when the user wants the original fixed quality filter. It passes a row when any one of `currentScore`, `historyRankScore`, `hotListScore`, `rankRecordScore`, or `rankingScore` is at least `10`; `topScore` is intentionally excluded. Incomplete score evidence is unresolved and must not be silently classified as low quality. The threshold and participating fields are internal fixed semantics, not caller-controlled request parameters.
7. Use `get_run` to follow durable progress. `waiting_quota` is a normal persisted state. Read per-processor state alongside task state. A login wait, CAPTCHA, 401, route mismatch, adapter mismatch, partial result, or configured limit is a real state; do not describe it as success.
8. If a run is interrupted, call `resume_run`. Use `pause_run` or `cancel_run` only for the specific requested run. Failed, timed-out, challenged, and quota-limited batches are never replayed automatically.
9. `check_candidate_qualifications` has two mutually exclusive high-level operations. `automatic_query` is only an explicit 1–30 creator recheck for a non-semi-auto run: it submits exactly one collection-sub-backend request, consumes the persisted global rolling budget, never retries automatically, and never sends an invitation. For an original regional `semi_auto` run, automatic querying is forbidden. The user queries the official sub-backend manually, then `manual_import` accepts 1–30 structured rows containing `handle`, raw `anchorStatusCode`, and optional raw reason/invitation-type codes. It matches normalized handles only to candidates in that run and persists the mapped result and fixed provenance; it performs no browser or network request, consumes no qualification budget, and triggers no recursive ranking expansion. Unknown, ambiguous, cross-run, duplicate, conflicting, or unknown-code rows reject the whole import.
10. Call `preview_candidates` first to report count, source, freshness, and field coverage without dumping identities.
11. Call `query_candidates` when the user's request requires the actual streamer list. Supply a short audit reason grounded in that request.
12. Call `prepare_handoff` only for a reviewed set whose TikTok candidates have this run's official `available` result under a market-matched collection-backstage preflight; use `qualificationStatus: available` in the selection. The backend's status `0` is the eligibility and market decision: a public card's separate `creatorCountryCode` may remain unknown, so do not require or invent it. The tool rejects a mixed or unresolved TikTok set instead of silently handing it to the digital employee. Each row carries its actual discovery method and source URL. Report `batchId`, `datasetHash`, count, and `pending_review` status.
13. Call `commit_handoff` only after the user explicitly approves that exact batch and hash. It writes an immutable local outbox item; it still does not contact anyone.
14. Use collection-data cleanup only when the user explicitly asks to delete local collection history by a concrete cutoff. Call `preview_collection_cleanup` first with an ISO timestamp and show the user its canonical `cutoff`, every `deleteCounts` and `protectedCounts` field, and `recoverability` (`recoverable: false`, `backupCreated: false`). Do not call `commit_collection_cleanup` until the user approves that exact preview and understands that no backup is created. Commit with the unchanged cutoff, `previewHash`, short-lived `confirmationProof`, and `userConfirmed: true`. A stale or expired preview, changed hash, busy collector, or failed commit requires a new preview and renewed user approval; never retry it automatically. Do not print, persist, or place the confirmation proof or deleted-row payloads in chat, logs, or audit details.

For a request such as "最近 N 个", do not assume the svip backend's page order is newest-first. Set an explicit `recordedAfter`/`recordedBefore` window (`YYYY-MM-DD HH:mm:ss`), collect until `result.sourceReconciled` is true, and then select the first N candidates from the locally audited `observedAt`-descending query. If the run stopped at `configured_candidate_limit` before source reconciliation, describe it only as N candidates from that time window, not the latest N.

`result.completionScope` is part of the result: `source_reconciled` proves the filtered svip source was exhausted and count-reconciled; `configured_candidate_limit` proves only that the requested bounded selection was filled; `partial_source` must be resumed or explicitly reported as partial.

## Invariants

- TikTok discovery, the creator-collection sub-backend, the guild-wide operations backend, and svip use physically separate persistent browser profiles. Never move Cookie, Token, local storage, or credentials between them.
- Keep the independent US TikTok-discovery node and the one-to-three country lanes distinct. Each configured country has exactly one collection proxy. `collection_backstage` shares WorkID 1's country node; WorkID 2 and 3 remain their own country lanes. Feed rows stay bound to the corresponding WorkID 1–3 lane through their first enrichment/ranking cycle. Ranking-derived rows reset to WorkID 4, preserve their ranking-scope country, and use the matching verified country lane; do not call the original `MobileSettings[0]` fallback a US route without evidence. Every run rechecks the US discovery exit plus every selected country lane. Preserve the original distinction between one shared broad market (`CountryData.Code`, such as MENA/CCA) and each lane's member-country code and country-matched proxy.
- Do not ask the user to paste credentials, cookies, tokens, QR payloads, or local-storage values into chat.
- Never describe the locally generated Core encryption key as a TKsoft/vendor key. User-owned Core is independent of vendor login. The optional original published source has a separate dependency on the publisher configuration and original format, explicitly labeled by provenance.
- The original country bundle's mobile `X-Tt-Token` is supplier authentication material. Under the user's explicit instruction to replicate the original authorization flow, the opt-in loader may use its current publicly distributed encrypted bundle for fixed read-only TikTok ranking requests. Cache only the encrypted bundle with owner-only permissions; decrypt and attach credentials inside the opaque provider, never through MCP, logs or chat. Without this opt-in or user-owned mobile authorization, fail closed. Never relabel a Web login cookie as mobile authorization; never reuse this source for vendor login, HMD, uploads or other platform writes.
- `clear_mobile_authorization` is destructive local credential removal. Call it only after the user explicitly confirms, never while a run or qualification batch is active, and report only the resulting readiness state.
- Collection-data cleanup is a separate irreversible operation and must never be used to reset a login or clear Core/mobile authorization. It may delete old terminal runs, checkpoints, discovery queue rows, observations, safely unreferenced prospects, expired qualification history, and uncommitted `pending_review` handoffs. It always preserves audit events, approved/dispatched or outbox-linked handoffs, every outbox item, sessions and browser-profile/login material, route/Core configuration, nonterminal or recently finished runs, and qualification attempts inside the rolling 24-hour safety window. Report the committed per-table counts, cutoff, audit ID, and non-recoverable state.
- Do not expose or improvise arbitrary click, evaluate, selector, HTTP, or script operations. Use only the versioned high-level adapters behind the MCP tools.
- Treat `null` as unknown. Never convert missing followers, eligibility, diamonds, live status, or country into zero or false.
- Treat each automatic collection-sub-backend query batch as one query allowance. Persist every attempted request before dispatch. Enforce the active 50–55 hourly target with hard ceiling 55, the active 145–150 rolling-24-hour target with hard ceiling 150, and a 60–80 second interval. Vary only downward from a selected ceiling/target; do not make up extra capacity. Do not reinterpret these as creator counts. Solving a manual verification must never replay the request; a new automatic query always requires a new explicit invocation. A `manual_import` is a local association of results the user already queried themselves, creates no `qualification_batches` attempt, and consumes zero allowance.
- Preserve source, observed time, adapter version, confidence, run ID, and completion reason when evaluating a candidate list.
- This skill may use only the dedicated creator-collection sub-backend. It does not operate the guild-wide control backend, manage the official account, or talk to creators. Those are separate systems.
