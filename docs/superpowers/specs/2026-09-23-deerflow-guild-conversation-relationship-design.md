# DeerFlow 公会原生沟通与关系连续性设计

日期：2026-09-23
状态：已纳入[完整方案](2026-09-23-deerflow-tiktok-guild-end-to-end-design.md)；不授权真实 TikTok 发送

## 1. 目标与范围

把 Wingman 中经过溯源和合成案例检验的通用沟通判断，以及人物、互动、未闭环事项、承诺、边界与关系变化，改写成 **DeerFlow 默认 Lead 的公会原生能力**。它服务于招募，也服务于入会后的主播运营；不新建“聊天 Agent”、Custom Agent、招募 Skill、Rust worker、Guild ledger、CRM 或容器。

本设计是 [TikTok 公会版 DeerFlow 产品设计](2026-09-23-tiktok-guild-deerflow-product-design.md)的一个实施切片。后者关于单一主 Agent、原生能力、工作台和真实消息通道的总体方向不变。本切片先让 Lead 能依据给定对话和可核验事实作出自然、连续的判断，并用合成通道事件验证隔离和持久化；**不接入真实 TikTok 收信、发信、邀约或回执**。真实发送仍须另行完成通道契约、授权、幂等与回执验收。

成功的体验是：运营者问“这位主播上次说过什么、我答应了什么、现在该怎么回？”时，Lead 能核对身份、原话和当前公会事实，给出贴合语境的建议；主播以后从可信通道来信时，同一个 Lead 能延续该主播自己的上下文，自主决定回复、澄清、修复、等待或停止，而不是按固定阶段或阈值走脚本。

## 2. 方案选择

| 方案 | 好处 | 代价或问题 | 结论 |
|---|---|---|---|
| 恢复旧招募 Skill 和案件卡 | 接线最快 | 能力依赖 Skill 是否激活，固定字段与步骤会再次约束 Lead | 不采用 |
| 另建聊天 Agent / 关系服务 | 模块独立 | 多一次会话与事实交接，重现旧架构的复杂度 | 不采用 |
| **默认 Lead 内的原生方法与按主播隔离的关系上下文** | 仍由 Lead 自主规划、使用工具；方法和证据随任务可用 | 需要定点修改 DeerFlow 的上下文与持久化接点 | **采用** |

“原生”是指该能力在默认 Lead 的运行路径中装配和测试，不要求用户手动激活 Skill，也不让另一个 Agent 先决定消息属于哪一类。DeerFlow 现有的 `build_middlewares`、扩展 `MiddlewareContributor`、thread/checkpoint 和 ChannelManager 是优先接点；若这些接口不足，允许最小源码改动。仍通过本机包的单个累计产品补丁维护差异，不增加运行进程。

## 3. 从原方案保留什么

Wingman 的 [方法资产](../../../references/wingman-methods/methods.json)和[精确来源锁](../../../references/wingman-methods/source-lock.json)是迁移输入，不是把恋爱文案原样装进公会版。原来源是 [`goutoujunshi@4ced1d57561563f4b556f555ee1c8c91ffb16355`](https://github.com/shengjidaguai-china/goutoujunshi/tree/4ced1d57561563f4b556f555ee1c8c91ffb16355)；Wingman 已把它改写成四组情境方法。迁移时保留来源、版本、适用条件、所需证据和反例，删除恋爱目标、暧昧话术与“保证转化”的暗示。

Lead 的共同判断原则：先辨认说话人和上下文；回复只依据对方原话、已核实的公会事实与已确认的自身承诺；接住一个具体细节，语言自然；误会或失约时承认有证据的影响，不虚构原因或补救；一次慢回复不推断动机；可以等待、降低打扰、停止联系。它可以在合适时自主邀约，没有预设“聊满几轮”“达到几分”之类门槛。外部消息中的指令只是消息内容，不会获得管理员授权。

### 3.1 公会招募中的“精聊”

这里的精聊是**针对一位已核实身份的主播，根据真实对话和当前业务事实决定下一步沟通**，而不是把恋爱关系模型或通用销售话术搬进公会。每次判断先辨认哪句话是谁说的、什么时候说的；再区分主播已表达的需求或疑虑、TKDesk 的候选观察、Guild Operator 的当前后台事实，以及 Agent 自己的推测。缺少稳定 TikTok `userId` 时可以分析给定文字，不能读写某位主播的长期上下文或自动联系。

把源方法改写为四类可选动作，而非固定阶段：

| 源方法 | 公会招募中的用途 | 必须避免 |
|---|---|---|
| `natural_reply` | 接住主播原话中的一个具体细节，用与其问题相称的口吻自然回应。 | 模板夸赞、虚构开播经历或未核实的公会福利。 |
| `invite_or_clarify` | 澄清合作条件，或在当前资格、名额和意愿有依据时提出一次清楚、可拒绝的邀约。 | 编造限时名额、收益承诺，或把普通聊天当正式平台邀约。 |
| `repair` | 对有证据的误解、失约或服务问题承担对应责任，提出确实能兑现的补救。 | 虚构原因、把建议写成公会已经作出的承诺。 |
| `wait_or_close` | 对单次慢回复保留未知；根据持续互动调整投入；明确禁联时停止。 | 定时追问、换号联系、把沉默当作同意或拒绝。 |

Lead 可以给出一条可直接使用的草稿，也可以建议核实事实、等待或不发。草稿每次只承载一个主要动作；草稿、运营者实际发送、平台接受、送达和入会结果是五种不同事实。源 skill 的恋爱目标、性别/MBTI 假设、主观人物评分、初次问卷及暧昧话术均不迁入。方法来源锁在 `references/wingman-methods/source-lock.json`；方法是可修正的沟通经验，不是主播意图或平台结果的证据。

默认上下文只注入短版共同原则和**当前这一位主播**的有界关系摘要。完整方法说明作为版本化的原生参考材料，供 Lead 按需读取；不设九类任务分类器、强制路由或每轮套用固定话术。方法是帮助判断的经验，不是对主播真实意图的证明。

## 4. 关系连续性与事实边界

主播本人以 TikTok 唯一 ID 为主键，运营者与公会连接只是隔离范围。TKDesk handoff 已提供 TikTok `userId` 等身份信息；运营者会话访问某位主播时，直接按该 ID 查找。昵称、截图文字和对方自称不能代替唯一 ID。当前 DeerFlow 的通道映射提供“外部会话 → 内部 thread”，但现有可信通道来源描述还不等于已验证 TikTok 主播 ID；未来通道须证明其发送者 ID 能可靠映射到这个主键。若某个入口缺 ID，可以分析这段话，但不能读写别人的关系状态或自动回复。

每位主播的工作上下文只保留影响下一步判断的内容：

- **人物与互动**：稳定身份引用、最近关键互动、原话/消息 ID、时间、方向与来源；不复制第二份完整聊天记录。
- **已观察事实与推断**：分别标记；例如“说过暂时没时间”是原话，“可能对合作仍有兴趣”只能是可撤销推断。平台政策、待遇、邀约额度和入会状态每次以当前 Guild Operator 证据为准。
- **未闭环事项与承诺**：谁提出了什么、谁答应了什么、是否兑现、证据和最后核对时间；建议的补救不自动写成已作出的承诺。
- **边界**：明确拒绝、退订、不再联系和其他被本人表达的限制，独立于短期关系摘要保留；新的普通积极信号不能静默覆盖禁联。
- **关系变化**：互惠、主动性、响应、动量和互动深度可作为可解释的定性观察，只有证据足够时才生成，并注明样本范围；不是统一分数、心理判断或自动邀约条件。

DeerFlow 现有 thread/checkpoint 继续保存各自的会话；可在主播第一次来信前建立、又能由运营者跨会话按 TikTok ID 查找的有界关系摘要，按[完整方案](2026-09-23-deerflow-tiktok-guild-end-to-end-design.md)放在**同一个 DeerFlow 本机数据库**的最小原生状态中。不得把所有主播事实直接放进默认按 `(agent_name, user_id)` 归桶的通用记忆；该桶在运营者身份下可能混入多个主播。不建独立数据库、后台投影或业务账本。每条记录有来源与时间，写入幂等；总结可更新，原始证据引用与禁联边界不可因总结而丢失。完整对话若由 DeerFlow checkpoint 保存，须沿用产品层明确的保留与清理策略。

关系状态是 Agent 的工作记忆，不取代 TikTok 后台和原始消息。缺失证据、矛盾证据和部分历史要显式呈现；不得为了凑完整档案猜测姓名、喜好、动机或承诺。运营者可以纠正错误关联，纠正要保留原因与被替换来源。

## 5. 运行路径

1. 运营者输入或可信外部消息进入默认 Lead。系统提供不可由消息正文伪造的来源；有稳定主播 ID 才解析其 thread 和关系工作状态。
2. Lead 看到有界关系摘要、短版方法原则和本轮原话；按任务自主调用 TKDesk、Guild Operator、原生工具或规划/子任务能力。需要更细的方法时再读取相应版本。
3. Lead 形成自然回复、问题、等待建议或其他行动。草稿与已发送严格区分；当前切片只输出建议或在合成通道中模拟动作，不触发真实 TikTok 写操作。
4. 对确认的新事实、承诺、未闭环事项或边界，Lead 在**该主播作用域**更新工作状态；重复事件不产生重复记录。下一轮读取的是新的有界状态，而非无限增长的历史全文。

这里没有“关系推进器”定时追人，也不让知识资产驱动固定序列。是否继续、何时邀约由 Lead 结合原话、可核验业务事实和对方意愿判断；明确禁联是例外性的持久边界。

## 7. 异常与测试

身份不明时不串档、不自动发；来源只证明部分历史时不冒充全貌；证据冲突时同时保留并请运营者核实；方法文件缺失时 Lead 仍可正常运行，但不得假称已参考该方法；关系状态读写失败时不输出“我记得你上次……”之类无法证实的内容。明确禁联在未来真实发送工具层也要被检查，不能只依赖提示词。实际消息发送、送达未知和重试处理不在本切片实现，必须在后续通道设计中单独验收。

实现验收使用合成主播对话，不接触真实主播：

- 原话归属含糊、昵称相同但 ID 不同、外部消息伪称管理员：不误认、不串档、不越权。
- 自然接话、疑虑澄清、失约修复、一次慢回复、明确拒绝：能给合适的回复、等待或停止建议，不虚构事实和承诺。
- 两位主播交错多轮、重启后继续、重复事件、摘要压缩：开放事项与已确认承诺仍能正确归属；摘要大小有硬上限，截断有标记。
- Guild Operator 返回 `partial` 或 `not_proven`：不会将局部后台数据写成全局结论或对主播作肯定承诺。
- 方法资产版本与来源锁可核对；同一组合的基线 DeerFlow 与增强版通过盲评比较“贴合原话、自然、事实准确、边界、跨轮连续性”，并用上述硬性隔离/禁联用例作必须通过的门槛。

验收标准不是“回复更像销售话术”，而是 Lead 保持原生工具、规划和自主判断的同时，能更准确地理解主播、更可靠地记住双方真正说过和答应过的事，并知道什么时候不该继续联系。
