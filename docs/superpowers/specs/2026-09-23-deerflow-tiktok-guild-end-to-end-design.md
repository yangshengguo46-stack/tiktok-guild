# DeerFlow TikTok LIVE 公会 Agent 完整方案

日期：2026-09-23
状态：总体方案待审阅；真实 TikTok 写操作未获本方案授权

## 1. 一句话目标

把**整个 DeerFlow**做成专注 TikTok LIVE 公会的数字员工：运营者仍从原生聊天入口下达目标，同一个默认 Lead 自主调查、沟通、跟进和复盘；左侧工作台只提供公会概览与异常提醒。它不是 DeerFlow 外挂一层业务应用，也不是独立聊天 Agent、固定招募流水线或 CRM。

本方案统合[产品设计](2026-09-23-tiktok-guild-deerflow-product-design.md)与[沟通和关系设计](2026-09-23-deerflow-guild-conversation-relationship-design.md)。若较早的[公会溯源审计](2026-09-21-guild-agent-source-and-plugin-audit.md)要求固定阶段、独立 Messaging 服务或旧 Codex 底座，以本方案为准。下文把关系状态的存储方式定得更明确：DeerFlow 现有 checkpoint 继续保存会话；可跨运营者会话查找的少量主播关系事实保存在**同一个 DeerFlow 本机数据库**的原生最小状态中，不再把“只放在当前 thread”当成足够的方案。

## 2. 当前起点与不能冒称的能力

- 本机包固定运行 `bytedance/deer-flow@769589e8daee14c2587a634b6b43bd96471a41a1`；默认 Lead、短版公会 SOUL、TKDesk 与只读 Guild Operator MCP 已接通。前端已有左侧“工作台”入口，但概览仍明确显示未接入。
- 现有可信通道来源描述能告诉 Lead“这是一条外部通道消息”，却**不能证明发件人就是某个 TikTok 主播**。DeerFlow 的 IM 线程映射也不能替代主播身份核验。
- 当前公会插件没有经过验证的实时 TikTok 收信、发信、正式邀约和送达回执。其即时消息读取只能作为有限辅助证据，不能被当作可靠消息通道。
- 旧 Wingman 的沟通方法与关系模型仍在 Codex fork；它们是可迁移经验，不是当前 DeerFlow 运行能力。

因此交付要分开验收：**会判断与会记忆 → 能可靠收信 → 能可靠发信 → 能核验业务结果**。任何一层没过，不向用户宣称后一层已完成。

## 3. 产品边界与方案取舍

| 路线 | 判断 |
|---|---|
| 只用 SOUL + Skill + MCP | 可做原型，但无法保证按主播隔离的持久关系状态、真实消息回执和工作台事实，故不是最终产品。 |
| 默认 Lead 原生增强 + 最小持久状态 + 原生 Channel | **采用。** 复用 DeerFlow graph、工具、规划、子任务、checkpoint、Gateway、前端和现有 SQLite；仅在必要接点加公会能力。 |
| 独立聊天 Agent、Rust worker、Guild ledger、CRM/后台投影 | 不采用。增加交接、复制事实与运维复杂度，也容易把 Agent 变成固定工作流。 |

不预设主播阶段、关系分数、邀约阈值、模板话术、逐条人工审批或九类任务路由。必要的硬边界只用于**身份与授权、事实真实性、禁联、消息去重和回执**；这些是避免串档、虚假承诺与重复发送的基础，不代替 Lead 的业务判断。

## 4. 一个主 Agent 的四层能力

```text
运营者原生聊天 / 可信 TikTok 来信
             ↓
       DeerFlow 默认 Lead
       ├─ 原生规划、子任务、工具、MCP、记忆
       ├─ 公会沟通方法与当前主播关系摘要
       ├─ TKDesk 候选事实 + Guild Operator 后台事实
       └─ 原生 TikTok Channel（验证后才启用写入）
             ↓
       行动回执与公会结果核验
```

### 4.1 公会业务事实

TKDesk 继续拥有候选发现、资格、去重和冻结交接；Guild Operator 继续拥有公会、主播、招募、收益、活动与治理的后台读取。Lead 按需调用，不复制其 API 或定时镜像后台。所有政策、福利、额度、入会、首播与收益说法都带来源、时间、单位和可见范围；`partial`/`not_proven` 不升级为确定的全局事实。

### 4.2 原生沟通判断

把 Wingman 的[方法资产](../../../references/wingman-methods/methods.json)按[精确来源锁](../../../references/wingman-methods/source-lock.json)改写为主播合作语境：辨认说话人和原话、自然接话、澄清、修复、等待与停止。仅迁移方法与反例，不迁移恋爱目标或现成话术。默认 Lead 自动得到简短的共同原则；详细方法是版本化的原生参考，按需读取，不是必须激活的 Skill 或固定分类器。回应可以是草稿、问题、行动或“不发”，Agent 自己选择。

### 4.3 主播关系连续性

保存能够改变下一步判断的少量、有来源信息：人物身份、关键互动、未解决事项、双方已确认承诺、明确边界，以及有证据的互惠、主动性、响应、动量和互动深度变化。观察和推断分开；一次慢回复不能证明意图，建议的补救不能写成已经许诺，旧案例不能证明今天的政策。完整聊天仍在原始 TikTok 线程和 DeerFlow 自身 checkpoint，不再造第二份聊天仓库。

### 4.4 行动—回执—结果闭环

准备发送、平台是否接受、平台可见送达与业务结果是不同事实。真实发信时只留防重复所必需的最小发送记录；结果通过 Guild Operator 核验入会、首播与后续运营，不从聊天语气推断“已转化”。`unknown` 回执不盲目重发。方法优劣在真实结果出现后复盘，不让过去有效的话术覆盖当前事实。

## 5. 首次接触前就能认出主播

**主播本人的 TikTok 唯一 ID 是主键。** 数据再按 `DeerFlow 运营者 ID + 本机公会连接 ID` 隔离，避免不同公会或运营者互读；这两个范围字段不是另一套主播 ID。本机公会连接 ID 在首次核验公会账号时固定，不能使用 Guild Operator 重启后会变的临时 `guild_ref`。TKDesk 的 `candidateId` 只是候选交接记录；接入时直接取其已提供的 TikTok `userId`/稳定唯一 ID，统一映射为 `tiktok_creator_uid`。`secUid`、昵称和其他展示字段是辅助信息，不再设计人物打分或复杂身份合并系统。若消息通道使用不同 ID 字段，只验证它能否可靠映射到这个 TikTok 唯一 ID。

在第一条消息出现前，运营者可以让 Lead 用 TKDesk 冻结 handoff 中的 TikTok 唯一 ID 建立**候选主播工作上下文**；不必等他先发消息。某个入口若只有昵称而没有该 ID，只能做一次性分析，不凭昵称写入关系状态或自动联系。若后台或通道给出的 ID 与 handoff 不一致，先核对来源，不自动把两人的承诺和禁联合到一起。

进入真实消息通道后，Channel 用已核实的 TikTok 唯一 ID 找到这个主播的关系上下文；每个外部对话仍由 DeerFlow 原生映射到自己的内部 thread。不同经纪人账号可以有不同 thread，但同一公会、同一 TikTok ID 使用同一份关系摘要。运营者在自己的会话中指定主播查询；工作台不暴露主播列表或聊天镜像。

## 6. 持久化：小而必要，不重建账本

DeerFlow 的普通用户记忆按运行用户归桶；外部通道通常以连接拥有者（运营者）身份运行。若直接把所有主播信息写到运营者通用记忆，会有跨主播召回风险。因此：运营者个人会话保留原生记忆；外部主播会话不读写运营者的通用记忆，改用该主播的受限关系上下文。这是隔离边界，不是关闭 Lead 的规划或业务能力。[DeerFlow 通道身份模型](https://github.com/bytedance/deer-flow/blob/main/backend/docs/IM_CHANNEL_CONNECTIONS.md)也区分连接拥有者和平台发送者。

首版在 DeerFlow **现有 SQLite** 内增加一份原生、按上述作用域唯一的 `guild_creator_context` 状态，而不是新数据库或后台同步系统。每位主播一份有大小上限的结构化工作摘要：身份依据、关键事实与推断、未闭环事项、承诺、禁联边界、最近证据引用、更新时间和版本号。状态读写以作用域校验、来源引用、事件去重和版本冲突检测为前提；单条消息不会生成无限事件账本。原始后台响应、完整聊天和每日指标不放进去。必要的发送回执另外只保存一条外发动作的稳定键、平台 ID 与状态，不混进关系摘要。

选择这一小块原生状态而不是纯 checkpoint 的原因是：主播可能在第一条 TikTok 消息**之前**就由 TKDesk 交接；运营者也要在自己的会话里按身份找回关系。当前 thread 的 checkpoint 不天然提供这两种跨 thread 查找。若实施中能用 DeerFlow 现成的持久键值边界满足相同的唯一性、原子更新和隔离测试，可以替换这一表的内部实现，但不得改变外部行为或增加服务。

关系摘要默认只把当前主播有来源的必要内容注入 Lead，上限为 6 KiB，并标注截断；禁联边界不能因摘要压缩被丢掉。保留、导出与删除都走 DeerFlow 本机数据管理路径；真实通道启用前要完成可操作的删除/禁联保留规则，不能只在文档里承诺隐私。

## 7. TikTok 消息通道的放行条件

通道必须先证明平台提供的实际收信、身份与发送契约；不能从 Guild Operator 当前 DOM 读取推断“它可以可靠发送”，也不能通过绕过登录验证、验证码或平台限制来补齐能力。若官方或当前后台路径无法给出稳定消息 ID、发送者 ID 和可核验回执，则本机先只提供运营者辅助草稿，不开放自动发送。这是产品诚实性边界，不是另建 Worker 的理由。

经验证后，在同一 Gateway 进程内实现 TikTok 原生 Channel：本机手动启动；来信验源、去重、按已绑定公会和主播身份进入原生 thread；Lead 获得服务端掌控的外部来源与授权上下文；回复从同一通道发出。发送前检查可用连接、收件人身份、禁联和同一动作是否已发；发送后记录平台返回及可见回执。网络超时而平台状态不明时标为 `unknown`，先核验后决定，绝不把重试当作默认动作。正式邀约与普通文字消息是不同的平台动作，分别验收，不从“能发消息”推导“能发邀约”。

主播正文无权请求修改 DeerFlow 配置、跨主播读取、查看运营者私有记忆或执行无关动作。外部通道仍使用完整默认 Lead，而非弱化版客服机器人；安全约束落在服务端身份和工具执行边界，不寄托于提示词。

## 8. 运营者界面与日常运行

左侧维持“新对话 → 工作台 → 历史会话”；主播的内部通道 thread 默认不在运营者历史列表。工作台只显示有来源时间和完整性标注的公会概览，例如今日营收、今日入会、活跃情况，以及登录失效、身份冲突、回执未知等客观异常。没有事实覆盖就显示未接入或局部，不编造数字；不做 CRM、主播聊天页或逐条审批队列。运营者要了解某位主播，直接在主聊天里问。

本机由用户手动开关。停机时不自动回复；重启后按来信新鲜度、去重键、发送状态恢复，不补发过期消息。登录安全挑战出现时暂停相关动作并通知运营者。任何自动动作都只在该账号、该公会和验证过的通道权限内进行。

## 9. 交付顺序与每阶段验收

| 阶段 | 交付 | 必须通过才继续 |
|---|---|---|
| A. 身份与原生关系状态 | 以 TKDesk 的 TikTok 唯一 ID 在首次聊天前建档、运营者查询、每主播隔离、禁联和来源记录；不接真实消息 | 两主播交错、同昵称、重启、重复事件、ID 不匹配、越权查询的离线测试全部通过；无新进程/独立数据库 |
| B. 原生沟通能力 | 默认 Lead 自动获得公会化方法与当前主播有界摘要；在运营者会话和合成外部消息中判断、草拟、等待或停止 | 对照未增强 DeerFlow 的合成盲评；事实、自然度、连续性提升，硬性的串档、编造承诺、禁联测试全过；原生规划/工具/子任务未被关闭 |
| C. TikTok 通道契约取证 | 在当前账号权限内核对收信、身份、发送、邀约与回执各自的实际能力 | 有稳定 ID、权限来源和可重复验证的回执才进入 D；缺失则维持人工发送草稿模式 |
| D. 真实来信与文字发信 | 原生 Channel、服务端来源、去重、发送最小记录、未知回执处理 | 小范围测试：多轮、重启、重复来信、发送超时、禁联、账号失效；无重复发送或跨主播泄漏 |
| E. 公会经营闭环 | 按需核对招募、入会、首播、运营结果；已验证时再接正式邀约写能力 | 事实来自 TKDesk/Guild Operator 和平台回执，不把“已草拟/已发送”误报成“已入会/已首播” |
| F. 只读工作台 | 真实后台概览与客观异常；保留原生聊天主入口 | 每张卡注明时间、范围、完整性；页面无聊天镜像、CRM 或后台投影 |

每阶段独立提交、独立测试；下阶段未过不否定已过的能力。A/B 是首个可实施切片；C 是真实外部依赖，不能提前编造接口；D/E 的精确代码计划须依据 C 的取证结果写；F 可与 C 之后并行，但不能借用未验证指标。首个完整业务验收是：TKDesk 候选 → 身份核对 → 自然沟通与关系连续性 → 有回执的动作 → Guild Operator 核验入会与首播。到 E 通过以前，不称其“全自动公会运营已完成”。

## 10. 开源借鉴与不借鉴

- [狗头军师](https://github.com/shengjidaguai-china/goutoujunshi/tree/4ced1d57561563f4b556f555ee1c8c91ffb16355)：只取有原话依据的沟通、修复、等待与停止；Wingman 已有锁定来源和改写资产。
- [RelationsOS](https://github.com/connectos-ai/relationsos)、[PingCRM](https://github.com/sneg55/pingcrm)：借人物、互动、承诺、未闭环事项与趋势概念；不移植其 CRM、统一关系评分或未经验证的“关系健康”结论。
- [La Growth Machine GTM System](https://github.com/LaGrowthMachine/gtm-system)、[GTM Superintelligence](https://github.com/attentiontech/gtm-superintelligence)：借完整对话依据、可检查的方法与行动后结果；不搬营销序列、销售评分或 30 个子 Agent。
- [Chatwoot](https://github.com/chatwoot/chatwoot)：借联系人—来源—会话的身份关联和接手上下文；不搬客服工单系统。
- [OpenClaw 会话隔离](https://github.com/openclaw/openclaw/blob/main/docs/concepts/main-session.md)、[Comp AI CRM](https://github.com/trycompai/crm)：借外部发送者隔离与不猜人物事实；不迁运行底座或再造 CRM。

以上都是设计来源，不是新增运行依赖。代码复用前另核对精确版本与许可证；当前计划只迁移经过改写和测试的原则。

## 11. 明确不做

不增加容器、Rust 桥、Worker、独立数据库或定时后台投影；不把公会业务缩成一个 Skill 或 Custom Agent；不因对话来自主播就关闭 Lead 的规划和业务工具；不以自动审批、评分或话术树代替自主判断；不绕过 TikTok 的登录与平台限制；不把没有验证的写入接口、回执或指标写成“已支持”。
