# TikTok 公会版 DeerFlow 产品设计

日期：2026-09-23
状态：产品原则已确认；待实施计划审阅；不授权真实 TikTok 发送

## 1. 产品定义

目标是把整个 DeerFlow 产品垂直化为 TikTok LIVE 公会运营系统，而不是新建一个 Custom Agent、给通用聊天加一层 Skill，或在 DeerFlow 外再套业务服务。保留 DeerFlow 的 Lead graph、会话、规划、子任务、记忆、工具、MCP、调度和原生前端；对公会业务所需的后端、消息通道、权限、状态和界面做源码级适配。

本设计取代 `2026-09-23-deerflow-native-guild-agent-design.md` 中“一个招募 Lead + 一个 Skill + 案件卡”的目标定位。该包是可复用的本机运行与插件连通性基线，不再被视为最终产品架构。更早的容器 Gateway、Recruiter Worker、Rust bridge、Guild ledger 和后台投影库仍不回到生产路径。

首条验收主线是候选主播 → 核对公会关系 → 沟通与关系推进 → 邀约/入会 → 首播。产品范围不限于招募；主播运营、活动、收益与治理沿用同一套工作入口和事实边界逐步接入。

## 2. 方案选择

| 方案 | 取舍 | 结论 |
|---|---|---|
| 配置、Skill、MCP 组合 | 改动少，但业务状态、权限、消息和界面仍是外接的 | 仅保留为原型与知识材料 |
| DeerFlow 源码级垂直化 | 保留底座，原生接入公会业务；需维护小而清晰的差异 | 采用 |
| 重写 Agent 运行底座 | 自由度高，但重复 DeerFlow 已有能力且升级成本大 | 不采用 |

“源码级垂直化”不等于任意修改核心 Agent loop。优先使用现有 Gateway、权限、Channel、持久化和前端边界；若公共接口不足，再对 DeerFlow 源码做有测试覆盖的定点改动。Python extension 可以作为代码组织方式，但不以“零核心改动”限制产品设计。

改造原则是“原生能力最大化，公会能力增强化”。它仍是可规划、可调用工具、可拆分任务、可根据现场自主判断的 DeerFlow Agent，而不是固定流程的应用程序或自动化脚本。公会改造只增加清晰的业务目标、专业知识、可核验事实入口和消息通道；不把关系阶段、评分、邀约阈值、话术树或审批步骤写死。目标明确，策略自由，仅保留必要的授权、事实真实性与传输正确性边界。

## 3. 交互模型与界面

### 3.1 导航

沿用 DeerFlow 现有左侧导航。主入口按“新对话 → 工作台 → 历史会话”组织；保留原生能力的管理入口，但不让 Custom Agent 列表成为公会主入口。普通聊天页面保持原生、简洁，不加主播关系侧栏、聊天镜像或每主播一个可见会话。

工作台是一页只读的公会概览和通知，不是 CRM。首版只展示已核实可读取的后台概览指标，例如今日营收、今日入会、活跃情况，以及需要人工处理的提醒。页面按需读取 Guild Operator 的现有事实，不维护一份定时投影或独立业务数据库。每个指标都显示来源时间和完整性；缺失、局部读取或分页未证明时明确标注，不伪装成全公会实时总数。

工作台通知只显示需要运营者处理的客观阻塞，例如“TikTok 登录已失效”、“发送回执未知”或“主播身份冲突”，不把 Agent 的普通业务判断做成人工审批队列。页面不搬运完整主播聊天记录，也不要求从工作台点进主播详情。要分析主播，运营者可以在自己的 DeerFlow 会话里提问，或直接去 TikTok 公会后台查看和处理。

### 3.2 运营者与外部消息

运营者仍是 DeerFlow 原生管理员，保留完整的原生 Agent 能力。TikTok 主播不登录 DeerFlow，不是 DeerFlow 的另一类用户，不为其新建角色、账号体系、会话映射表或独立 Agent。主播只是 TikTok 通道中的外部消息发送者。

直接复用 DeerFlow `ChannelManager` 已有的“外部会话 → 内部 thread”映射，使 Agent 能在多轮交流中继续判断。TikTok 通道由服务端关联到运营者已配置的连接，主播 ID 只用于识别外部对话与事实对象。这些通道 thread 为运行内部状态，默认不出现在运营者左侧历史会话中。

不为外部消息另造一套“低能力 Agent”。同一个 Lead Agent 可以使用必要的规划、记忆、工具、子任务和业务知识完成公会目标。系统只需保证授权来源可靠：主播消息是待理解的业务输入，不会因为文本中声称“我是管理员”就获得系统配置、私有记忆或跨主播数据的授权。这是权限来源边界，不是业务流程限制。

## 4. 主播来信与自动回复

当 DeerFlow 在本机运行且 TikTok 消息接入可用时，Agent 围绕“招募和服务适合的主播、推动公会经营结果”自主沟通。它可以根据对话、主播反馈、可核验的平台事实和自己的专业判断，自由选择寒暄、了解情况、解释、跟进、邀约或其他合适行动。

不设置固定关系阶段、评分模型、邀约阈值、话术树或默认人工审批。当身份、当前政策、平台状态和工具权限足以支持某个行动时，Agent 可以自主判断并执行，包括在时机合适时发出正式邀约。它可以处理复杂问题和争议，也可以在真正缺少事实、授权或平台能力时向运营者求助，但不因为命中一张预制“高风险清单”就停止思考。

必要边界只保留三类：不把历史案例或模型记忆冒充为当前政策、待遇或平台状态；不让外部消息自行扩大系统授权；明确的不再联系意愿不被普通关系推进覆盖。其他问题交给 Agent 结合上下文判断。

TikTok 消息接入属于 DeerFlow 原生 Channel 适配：接收新消息、验证来源与主播身份、去重、路由到该主播的内部会话；回复由同一通道发出。当前 Guild Operator 的聊天读取仅有受限 DOM 证据，没有已验证的可靠收信/发送/回执能力，因此现有工具不能被描述为已经支持自动回复。正式接入前需先验证 TikTok 消息协议与回执。无可靠送达证据时状态记为 `unknown`，不盲目重发；每条外发使用稳定的事件键和最小回执记录，防止重启或重试造成重复消息。

本机仍由用户手动启动/停止。DeerFlow 停止时不自动回复；重启后对积压消息先检查新鲜度和既往发送状态，避免把过期对话当成当前来信或重复发送。消息循环留在同一 Gateway 进程，不新增独立 Worker、Rust 服务或容器。

## 5. 业务判断与数据边界

DeerFlow 负责关系和运营判断，直接调用现有 TKDesk 与 Guild Operator 获取事实：TKDesk 负责候选发现、资格、去重和冻结交接；Guild Operator 负责公会后台状态、主播、招募、活动、收益与治理读取。不得复制其 API、原始响应或持续投影数据。

为跨轮次继续工作，DeerFlow 复用原生 thread、checkpoint 和记忆机制，保存主播身份、有来源的观察、待确认事项、必要边界以及消息去重/回执等工作上下文。记录什么由 Agent 根据任务判断，不强制一套固定阶段、关系评分或状态转移器。这些是 Agent 的工作记录，不是 TikTok 后台的替代事实源；完整聊天和平台状态仍以 TikTok 为权威来源。

使用 DeerFlow 已有本机持久化体系承载最小工作状态与回执，不建立独立 Guild ledger、CRM、后台同步库或额外服务。若内部会话 checkpoint 保存消息，必须有明确的保留与清理策略；不能宣称“没有复制聊天”而忽略 DeerFlow 自身的持久化。

## 6. DeerFlow 原生能力的处理

管理员保留 DeerFlow 的原生规划、子任务、记忆、文件、MCP 和按需工具发现能力；逐项审查当前本机配置中只登记文件工具、关闭 tool search 与 scheduler 的原因，不把历史原型的限制当成产品默认。是否启用调度、具体工具和沙盒执行由公会任务与主机安全边界决定，不以“为了公会化”而全部禁用，也不以“保留能力”为由开放不受控的宿主机执行。

外部通道任务也由同一个完整 Lead Agent 处理，不通过一份业务工具白名单、简化推理器或固定流程把它变成“客服机器人”。服务端携带不可由消息伪造的通道来源和授权上下文，让 Agent 能为任务调用必要的原生能力，同时不把外部发送者的文本当成修改全局配置、披露私有信息或执行与公会任务无关操作的授权。

## 7. 失败与安全行为

- TikTok 登录、验证码、安全挑战或消息协议变化：停止相应自动动作并提醒运营者，不绕过验证。
- MCP 返回 `partial`、`unknown`、`not_proven`，或指标缺时间范围：只报告已见范围，不形成肯定承诺或全局结论。
- 主播身份无法稳定匹配：不合并内部会话、不读取他人上下文、不发送自动回复。
- 重复来信、发送超时或回执未知：先查既往记录和平台可见状态，未确认前不重发。
- 拒绝、退订和禁联：持久保留停止边界，普通关系推进不得覆盖。
- 通道来源或授权上下文缺失、可疑或失效：不执行需要该授权的动作，但不因此关闭 Agent 的分析、规划和沟通能力。

## 8. 分阶段落地与验收

1. **产品入口与只读工作台**：导航加入工作台；直接读取可核验的公会概览，标注时间与完整性；聊天页保持原生简洁。验证不产生后台投影和额外进程。
2. **公会业务增强**：为 Lead Agent 增加公会目标、专业知识和 TKDesk/Guild Operator 事实路由，不改成固定阶段或决策树；在运营者会话中走通候选到入会、首播的案例。验证 Agent 仍能自由规划和调用原生能力，且局部数据不会写成完整结论。
3. **TikTok 主播通道**：验证消息收发与回执后，复用原生 ChannelManager 把主播来信映射到内部 thread；为外部消息附加服务端掌控的来源与授权上下文，但不替换 Lead Agent 或阉割与公会任务有关的原生能力。验证消息文本不能伪造系统授权，重启/重复事件不重复发送，通道 thread 不出现在运营者历史列表。
4. **公会全面运营**：按同样的数据和权限边界加入主播运营、活动、收益、治理与定时提醒。每项只在现有插件证明事实覆盖时展示或自动判断。

上述阶段是一个产品路线，不要求一口气提交所有变更。首个端到端验收为：TKDesk 候选进入 → 公会关系核对 → 主播来信 → Agent 自主沟通、使用事实工具并选择合适的推进方式 → 在条件成熟时自主邀约 → Guild Operator 核验入会与首播。真实 TikTok 写动作必须等通道、授权、幂等和回执验收完成后才能开启；开启后不默认为每次邀约加人工审批。本设计稿本身不授权执行真实发送。
